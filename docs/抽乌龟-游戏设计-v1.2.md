# 抽乌龟｜游戏设计与交互规范 v1.2

> **历史设计文档提示（v0.3.0 整理）：** 本文保留早期 v1.2 设计原貌，文中关于“当前原型 v0.1”“尚未实现”的开发状态已经过时。请优先阅读 [文档索引](文档索引.md)、[游戏规则](游戏规则.md)、[抽牌交互与界面](抽牌交互与界面.md)、[AI 策略与信息公平](AI策略与信息公平.md)及对应源码；这里仅作为早期设计留档。

版本：2026-11-04 · 状态：**规则与交互基线已确定；工程原型为 v0.1，不代表全部验收完成**

## 1. 项目目标与边界

- 2～6 人休闲纸牌游戏，支持真人、AI 与混合对战。
- 不使用真实货币、下注、概率操纵、赌博化视觉元素。
- PC 和移动端采用同一游戏规则与不同布局；移动端优先横屏，自然响应方向变化，不请求或强制旋转。
- 首版轻量实现，不依赖数据库、不依赖 Docker；可用单机 Node.js 进程管理实时房间。
- 核心优先级：规则正确 ＞ 信息公平 ＞ 抽牌可操作性 ＞ 网络可靠性 ＞ 动画装饰。

## 2. 核心规则（最终确定）

| 决策 | 规范 |
| --- | --- |
| 牌组 | 52 张标准扑克牌，不含大小王；每局随机移除 1 张并保密 |
| 发牌 | 剩余 51 张依次轮流发完，允许手牌数量不同 |
| 对子 | **两张点数相同**就成一对，花色不限，自动移至公开弃牌区 |
| 行动 | 座位顺时针轮流行动，当前玩家从其逆时针方向最近的一位仍持牌玩家抽一张 |
| 选牌 | 目标牌背全部相同；目标有多张牌时先选中再确认，只有一张时直接抽 |
| 洗序 | 允许主动洗序或手动拖动排列；一旦成为当前抽牌目标，本回合立即锁定手牌顺序 |
| 超时 | 自抽牌阶段开始 30 秒，未操作自动从目标手牌均匀随机抽取一张 |
| 结束 | 25 对牌全部弃掉，最后剩下一张未配对牌；持有者失败，其他人胜利 |
| 异常 | 断线者保留座位、手牌，由 AI 托管其操作；重连恢复原位置 |

**特殊情况纠正：** 当至少三人仍在局中时，一名只剩一张牌的玩家从另一名只剩一张牌的玩家手中抽得同点数的牌，**双方可能同时脱身**，而第三名玩家独自留下乌龟。这不违反“全局剩余牌始终为奇数”的条件，必须允许。

正常结算应始终满足：弃牌 50 张（25 对），手牌 1 张，开局移除 1 张；这两张牌点数必然相同、花色不同。

## 3. 抽牌完整交互

1. 服务器确定行动玩家与抽牌目标，目标在**回合开始前**锁定自己的牌序。
2. 展示目标背面手牌，全部可独立操作；超出宽度使用横向滚动，绝不压缩到无法点选。
3. 点击某张牌只表示“选中”；可切换目标。多张牌时点击“确认抽取”才提交。
4. 目标仅一张牌时直接点击抽牌，免二次确认。
5. 抽取的牌**加入抽牌玩家手牌末尾**，此行为是公开规则。未配对时不得对旁观者展示其牌面。
6. 若新牌形成对子，自动正面展示这一对并公开弃牌；成功配对不追加抽牌机会。
7. 将手牌清空的玩家立刻标为脱身；重新求出有效邻座与行动者。
8. 如果只剩一位玩家有牌，直接判定乌龟，揭晓被移除的牌及真正剩余的那张牌。

### 手动洗序与重排的公平定义

- 玩家可以在自己**未被抽牌**时手动重排，或点击“洗序”随机重排。
- 洗序/重排的**精确位置映射仅对本人可见**；其他玩家会得知“该玩家已重排”，从而不能持续利用旧位置映射。
- 对手进入抽牌阶段后冻结本轮手牌顺序。先后到达服务器的“回合锁定”“重排请求”按顺序严格判定。
- 对方已经选中的位置，在确认抽牌前不得由目标改变。
- 洗序绝不替换卡牌、改变点数、重洗牌组或触发配对。

## 4. AI 信息与记忆策略

### 4.1 信息访问边界

AI **允许**：自己手牌、目标牌数、公开弃牌、有效的历史观察、已知牌从自己手中流出的事实、位置变化是否已被洗序打乱、所有玩家公开手牌数量。

AI **禁止**：其他玩家的实时手牌牌面、隐藏牌的内部 ID、被移除的牌、未来随机数、越权读取服务器私有游戏状态。

工程约束：决策函数的输入必须是 `aiObservation` 构造出的脱敏数据，不应直接向策略函数传入全量房间/牌组对象。

### 4.2 记忆分层

| 类型 | 定义 | 可作为确定抽牌依据？ |
| --- | --- | --- |
| 自己当前手牌 | AI 实际持有的牌面 | 可以 |
| 公开对子 | 已经弃掉的两张牌及点数 | 可以参与合法推断 |
| 可追踪位置 | 自己明确知道被抽走的牌，且其进入对方手牌末尾后从未失去位置对应关系 | 可以 |
| 历史归属 | 曾经知道某玩家持有某点数，但其牌后来被重排/抽走 | 不可以当作确定位置 |
| 概率猜测 | 基于公开剩余牌数、行为习惯得出的估计 | 只能作为低置信度参考 |

位置记忆在目标**重排或洗序**、已知牌从目标手中被抽走、无法追踪的成对移除后失效；不得利用程序内部的 `card.id` 自动恢复。

### 4.3 抽牌策略

1. 若目标某个位置仍有**可确认**且与 AI 自己的点数相同的牌，优先抽该位置。
2. 若确认某些位置不能与自己配对，尽量避开这些位置。
3. 其余信息不足的所有位置等概率随机抽取；不虚构自己看不到的信息。
4. 公开弃牌可用于排除不可能的乌龟点数：某点数四张牌均已公开成对弃掉，则该点数不可能是乌龟。
5. AI 可以总结真人偏爱抽取左/右/中间的习惯，用于**自己重排时**合理摆放牌；不得为了诱导而令某张牌的命中区域更小。

**难度策略：** 首版不设置难度等级。AI 以公平为最高约束，信息不足时随机选择；不能承诺“每次一定聪明”，因为在完全隐藏的选择中不存在超越随机猜测的确定策略。

### 4.4 AI 重排策略（迭代要求）

- 只在自己未被锁定时操作；可依对手历史选位分布主动改变排列。
- 重排行为公开，精确排列对应关系保密。
- 必须与真人使用同一服务端操作接口及合法性约束。
- 原型 v0.1 已实现 AI 对已知位置的记忆抽牌，**尚未实现根据对手选位习惯主动重排**。

## 5. 大厅与房间规范

### 5.1 首页信息架构

首屏只保留三个同等明确的入口，**快速开始**为主视觉：

- **快速开始**：1 真人 + 3 AI，直接进行 4 人游戏。
- **创建房间**：设置上限 2～6 人，生成 6 位不易混淆的房间号，房主开始游戏。
- **加入房间**：输入房间号和昵称，进入等待房间。

附带低优先级入口“玩法与规则”；不强制注册、不引入积分商城、不设置下注。

### 5.2 房间状态

`等待加入（LOBBY） → 正在对局（PLAYING） → 已结算（FINISHED） → 房主再来一局（PLAYING）`

过期空房间可销毁。真人离开房间前，**不允许**开局中的陌生新玩家替代其座位；同一玩家携带原有效凭证才可恢复。

### 5.3 房主与成员权限

| 行为 | 房主 | 普通真人 | AI |
| --- | --- | --- | --- |
| 查看房间号和成员 | 是 | 是 | 不适用 |
| 邀请朋友加入 | 可分享房间号 | 可分享房间号 | 否 |
| 添加/移除 AI | 仅等待中可以 | 不可以 | 不可以 |
| 选择房间最大人数 | 创建时 | 不可以 | 不可以 |
| 开始新局/再来一局 | 可以 | 不可以 | 不可以 |
| 拖动/洗序自己的牌 | 可以 | 可以 | 遵守相同锁定规则 |
| 抽牌 | 到自己回合 | 到自己回合 | 到自己回合 |
| 中途主动退出 | 转由 AI 托管，尽可能转移房主身份 | 转由 AI 托管 | 不适用 |

至少有两名参与者（含 AI）才能开始；不要求房间达到人数上限。**不采用自动满员开局**，避免好友尚未安排完座位就突然开始。

### 5.4 联机与重连

- 通过服务端持有的唯一会话凭证恢复原座位；昵称不作为身份认证。
- 手持者只接收自己的牌面；其他玩家仅能获取公共计数和背面可选位置。
- 断线进入托管，正常继续游戏；恢复连接后停止托管。
- 30 秒回合限时由服务端决定，不以本地计时为准。
- 房间号只用于进入，不能替代会话身份凭证。
- 多次提交同一个抽牌操作只能成功一次；服务器检查玩家身份、当前行动者和预期回合序号。

原型说明：当前房间保存在 Node.js 进程内存；服务重启后**进行中的对局不可恢复**。商业化/高并发版本应另外设计持久化与多实例会话一致性。

## 6. PC 端牌桌布局

目标分辨率：1440×900、1366×768；最低建议为 1024×600。

| 区域 | 布局规范 |
| --- | --- |
| 顶部 | 游戏标志、房间号、连接状态、退出，尽量单行 |
| 对手座位 | 牌桌上缘，显示头像、昵称、剩余牌数和当前状态 |
| 中央牌桌 | 视觉主区域，占据可用高度大部分；绿色桌游毛毡、温暖木质边框 |
| 目标背面牌 | 中央偏上，最大化可选面积；数量过多时横向滚动 |
| 抽牌确认 | 目标牌列下方、易触达，选中后突出 |
| 状态信息 | 已配对 / 25、回合倒计时、当前持牌人数 |
| 我的手牌 | 固定在下方，正面展示；可横向滚动、拖动排序 |

正常操作尽量避免模态弹窗。配对提示、脱身提示可使用小型文字反馈；只有结算使用明显覆盖层。

## 7. 手机端牌桌布局

**横屏优先，不调用屏幕旋转权限、不会弹出“请旋转手机”的强制提示。** 竖屏保留可操作降级布局。

参考横屏视口：844×390、740×360、667×375。

| 区域 | 移动端尺寸与行为 |
| --- | --- |
| 顶栏 | 约 32～36px，保留退出及必要状态 |
| 对手座位 | 缩成紧凑卡片，可横向排列；避免盖住主要出牌区域 |
| 中央背面牌 | 建议 46～54px 宽、64～72px 高；**每张独立触摸**，超宽可滑动 |
| 抽牌确认 | 固定于牌列下方，切换选中无需弹窗 |
| 自己的牌 | 底部一行横向可滑动牌列，约 44～54px 宽；不强制弧形 |
| 排序 | 长按约 280ms 再左右拖动；普通滑动用于浏览手牌 |
| 洗序 | 底部右侧一个简洁按钮；锁定时禁用 |
| 安全区域 | 避开系统刘海、圆角和底部安全区域 |

必须避免“为展示全部牌而无限缩小”。人数多时通过横向滚动来维持可操作性；背面牌的有效触控区域目标至少约 44×44 CSS px。

## 8. 视觉方向

- **风格：** 温暖的桌游、纸牌、轻量休闲，不做赌场筹码风格。
- **主色：** 温暖浅米色页面 + 森林绿牌桌 + 木边 + 少量金黄强调色。
- **牌背：** 统一几何纹样；同一牌组每张牌背无差异。
- **功能按钮：** 形状、字重、大小统一，取消重复确认弹窗。
- **信息优先级：** 当前是谁抽谁 ＞ 要抽的牌 ＞ 我的手牌 ＞ 倒计时及弃牌统计。
- **动画：** 短、明确、不遮蔽牌面；减少动态效果设置应生效。

## 10. 工程建议与阶段划分

**M0：可运行原型** —— 一份可在 Node.js 20+ 上运行的单机服务，游戏、基础联机和 AI 成立，建立自动化规则测试。

**M1：体验打磨** —— 牌桌真实动效、目标背面牌触控优化、AI 主动重排、抽牌历史提示、完整多机型测试。

**M2：上线准备** —— HTTPS 与反向代理、访问与请求频率控制、运行监控、持久化、单实例异常恢复、对抗性联机测试。

注意：不应在 M0 阶段称为“生产级多人游戏”；其用途是快速验证玩法与交互。
